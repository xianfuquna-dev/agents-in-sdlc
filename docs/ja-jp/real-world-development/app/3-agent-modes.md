最初にプロジェクトに小さな機能を追加しました。より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って動作するため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを進めます。まず Issue を使って新機能を作成し、コードが有効で、機能が期待どおりに動作することを確かめてから、プロジェクトにマージします。

> [!NOTE]
> 機能開発を続ける間は、同じセッションを使います。通常は、作業するファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため、手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動で検証します。

機能の開発を続けながら、リポジトリの指示を更新し、既存の品質チェック スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログは拡大しており、訪問者がゲームをカテゴリや発行元で絞り込める必要があります。バックログの Issue には機能の説明がありますが、複数カテゴリの組み合わせ方など、実装前に合意すべき詳細があります。Plan モードで仕様を決めた後、範囲を限定した実装を Autopilot に許可します。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、より重要になります。ほとんどの開発者は、次のようなフローに沿って作業します。

1. 実装する内容の詳細が記載された Issue を開きます。
2. 構築する内容の計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードがレビューされ、継続的インテグレーション プロセスが成功したら、コードをマージします。

> [!NOTE]
> チームや組織によって詳細は異なりますが、ほとんどは上記の流れに沿っています。

この標準的なアプローチに従うことで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じ審査プロセスを経るようにできます。

## セッション モード

**セッション モード**では、エージェントにどの程度の自律性を与えるかを設定します。プロンプト フィールドの下にあるドロップダウンから設定でき、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次に進む前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律的に作業し、入力を待たずにコードを書き、テストを実行して、繰り返し改善します。

最初に Plan モードを使って計画をレビューし、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** の下にある Tailspin Toys リポジトリ フォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これは既存のシード済み Issue なので、新しい Issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした**新しい作業ツリー**を選びます。

    ![New session ボタンを指す矢印が表示された GitHub Copilot app の Issue ビュー](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに関連付けられていることを確認し、モード選択から **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは動作しない場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了してから再度開きます。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てると、Copilot がコードを書く前に進め方をレビューできます。Issue から開始したため、Copilot はすでに機能の要望をコンテキストとして把握しています。次のように送信します。

```plaintext
Build this feature.
```

Copilot の質問に答え、計画が Issue の受け入れ条件に沿っているか確認します。カテゴリと発行元によるフィルター、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確かめます。複数カテゴリの組み合わせ方や、該当するゲームがない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトで既存のツールを使った lint、ユニット テスト、E2E テスト、型チェックを含めます。フィルターの実装とテストに集中し、品質ワークフローを完了するまでは PR を作成しません。承認する前に計画の変更を依頼し、後で検証できるよう Issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に問題がなければ、**Approve and implement this plan** (または使用中のバージョンに相当するオプション) を選択します。承認によってモードも切り替わると決めつけず、現在のモードを確認してください。モード インジケーターに **Autopilot** と表示されていることを確かめます。

Copilot は実装を開始します。承認済みの計画に沿って作業を進め、コードを生成してテストも実行します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があります。計画を先に確認してください。Copilot が依存関係の不足やポートの競合を報告した場合は、チェック完了と判断する前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

ほかのコードと同様に、生成されたコードもマージする前にレビューする必要があります。コードをレビューし、サイトを実行して問題がないか確認しましょう。

1. **Changes** を開き、フィルターの実装とテストを確認します。
2. 複数カテゴリと発行元の組み合わせなど、結果が Issue と承認済みの補足事項に沿っているか確認します。変更が既存のリポジトリの指示にも従っていることを確かめます。
3. lint、ユニット テスト、E2E テスト、型チェックの結果を確認します。チェックのスキップは合格ではありません。
4. 失敗を解決し、実装を受け入れる前に該当するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして起動でき、ローカル サーバーを再利用する場合があります。テスト対象が前のレッスンのサーバーではなく、この worktree のサーバーであることを確認してください。

## 新機能を試す

コードに問題がなさそうでも、動作を確認する必要があります。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きましょう。

1. 次のプロンプトを使って、Copilot にアプリの起動とブラウザー キャンバスでのページ表示を依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果がそのカテゴリに合うことを確認します。フィルターをクリアしてから発行元を選び、結果がその発行元に合うことを確認します。
4. カテゴリと発行元を組み合わせ、結果を Issue および承認済みの計画と照合します。複数カテゴリに対応している場合は、合意した組み合わせの動作も検証します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットして、全件が再び表示されることを確認します。
6. 確認が終わったら、次のプロンプトを使って、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンでも同じセッションを使う

フィルター機能の PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次は、フィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後、セッションはそのままにしてかまいません。次のレッスンで同じセッションに戻ります。
